# Why this shape

Generated from `docs/decisions/README.md` by `npm run docs:decisions`. Do not edit this file; edit the index row and regenerate.

The template is one local-first vertical slice. An uncertain document waits for a person, and every posted value can name its evidence. The sections below give one decision each, followed by the verification limit.

## The seam an adopter changes first

The `Extractor` is the first seam, and the one the fixtures exercise. The demo reads one document shape with a template extractor plus an independent identity read; replacing `Extractor` with Document Intelligence or an LLM changes that adapter and leaves the pipeline, the gates, and the evidence invariant in place. The seam exists because extraction varies by document source while the decision rules must not.

The trade-off an adopter meets first is coverage. A second document shape costs a new extractor, not a new pipeline, and the fixtures state the shape the contract expects. `docs/adapters.md` names what each port must preserve, so a reader can replace one adapter without reading the rest of the tree.

## 0001: Local-first vertical slice

**Problem:** A template must be readable and runnable by an engineer judging the architecture and a hiring manager judging whether the author can ship, without an account, a key, or a cloud deployment.

**Options:** A hosted demo with a live model and a seeded cloud store; a local-first vertical slice with a local implementation of every port.

**Decision:** Ship one vertical slice that runs with `npm ci` then `npm run demo`; every port has a local implementation and the default path makes no network call.

**Cost:** One document shape, six fixtures, no OCR and no multi-tenant concerns; breadth is traded for a readable, runnable path.

**Falsification signal:** A clean clone needs a network call, an account, a key, or more than two minutes to reach the first screen.

**Undo:** `git revert -m 1 624c59e` removes the slice.

## 0002: No evidence, no post

**Problem:** An intake system that posts values without a trace cannot be audited or corrected with confidence; the failure is a plausible wrong value with no origin, not a crash.

**Options:** Log evidence but treat it as advisory; build one evidence entry per posted value and refuse a post that disagrees with it.

**Decision:** `post` builds an evidence entry per posted value and throws `IntakeError("no-evidence")` on a mismatch; operator input is evidence with its own source.

**Cost:** A legitimate post can fail when a producer forgets evidence, so the failure is loud and typed rather than silently accepted.

**Falsification signal:** A posted value has no evidence entry, or a value that differs from its evidence is posted without `IntakeError("no-evidence")`.

**Undo:** `git revert be9f17e` (also removes 0004's verify pass).

## 0003: Short-circuit before any model call

**Problem:** The common case is a clean order that matches the catalogue exactly; routing it through a model adds latency, cost, and a failure mode for no benefit.

**Options:** Call a model for every document and trust its confidence; run deterministic gates first and call the optional judge only for a held line.

**Decision:** `decide` runs the gates first and emits `decide.shortcircuit` with `modelCalls: 0` when every line matches; the judge runs only for a held line.

**Cost:** Two decision paths to keep tested, and the judge seam stays unexercised by the demo.

**Falsification signal:** A fully matched run calls the judge or emits a model call, or `decide.shortcircuit` is missing from its log.

**Undo:** `git revert 323c8bc` restores the pre-gate decision path.

## 0004: Verify after posting

**Problem:** A successful write is not proof that the value is still there or still correct; stores lose records and out-of-band edits happen after the post returns.

**Options:** Verify synchronously inside `post`; run a delayed `verify` pass that compares posted keys with the latest store revision.

**Decision:** `npm run verify` reads `post.written` keys, compares each with the latest revision, and reports `ok`, `missing`, or `drift`.

**Cost:** It compares against the local store only; a remote adapter must add its own read-back, and the limitation is stated wherever verification is described.

**Falsification signal:** `verify` reports `ok` for a key the store no longer holds or holds with a different value, or reports drift for an unchanged record.

**Undo:** `git revert be9f17e` (also removes 0002's evidence invariant).

## Verification limit

`npm run verify` compares each posted key with the local record store. It does not prove that a remote system still holds the record.
